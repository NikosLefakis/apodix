“Done” is not proof.

Apodix checks the work your AI agent says it finished. For every acceptance criterion, it shows what is proven, what is unproven and what is missing.

Green tests can still miss the point.

An agent can pass every test it wrote and still skip half of what you asked. Tests that pass tell you nothing about requirements nobody tested.

What the agent says

All three requirements are implemented. All 12 tests pass.
12 tests, 12 green

What Apodix finds

1 of 3 criteria proven

The 12 tests cover one requirement well. The other two are untested or untestable as written.

  • Discount over €100: proven
  • No-discount items: missing
  • Empty promo code: unproven

Three verdicts. No “probably”.

Every criterion ends in exactly one state, so a reviewer knows where to look.

Proven

A test guards it

The test passes today, and it fails when Apodix breaks the matching code on purpose.

Change 10% to 5% and the test goes red.

Unproven

A test exists, but guards nothing

The code may be right, but nothing would notice if it were wrong.

Delete the check and the test still passes.

Missing

Nothing covers it

No code or test relates to this requirement. The agent forgot it, or never understood it.

The words “no discount” appear nowhere in the diff.

How Apodix checks the work

The model never grades itself: the verdict comes from running code.

  1. Read the criteria

    Reads acceptance criteria from a markdown file and keeps each one’s ID. GitHub issues are next.

  2. Find the evidence

    Links each criterion to the tests marked to cover it, and records which code lines those tests ran.

  3. Break it on purpose

    Changes the matching code in a scratch copy and reruns the tests. A real guard test turns red.

  4. Stamp the verdict

    Returns Proven, Unproven or Missing for each criterion and sends the gaps back to the agent.

What it can’t prove yet.

A proof tool that overclaims is worse than none. Here is where the first version stops.

  • LanguagesPython with pytest first. TypeScript is next.
  • Kinds of rulesAnything a unit test can check. Visual layout and timing are out of scope for now.
  • Outside servicesPayments, email and other APIs need mocks. Apodix will say so when a rule depends on one.
  • Vague criteria“Make it feel fast” cannot be proven. Apodix flags it and asks for something measurable.
